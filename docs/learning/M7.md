# M7 and M8: paper trading and the locks in front of live trading

Written when the code was complete (2026-10-04). M7 itself ends only after
two months of paper trading and gate G3; M8 is switched on by you alone.

## What was built, and why this design

**Paper trading is the backtest engine fed live.** There is no second
implementation of fills, risk checks or event building: the paper runtime
(`gats.runtime.paper`) calls the same functions the backtest calls and
steps the same engine one item at a time. That is what makes "paper versus
backtest" a meaningful comparison at G3. A separate paper simulator would
drift, and the comparison would measure the drift.

**The account is rebuilt from a journal, not saved as a snapshot.** Every
filing, bar and reference price the engine was given is stored in order
(`paper_journal`). The engine is deterministic, so replaying the journal
gives the account back. Orders and fills are stored too, and a replay must
reproduce them: if changed code would decide differently, the run refuses
to continue rather than rewrite its history.

**Live trading is three locks, each opened by a person.** A switch that is
off by default; hard rupee caps that ship as "not set"; and an approval row
that only an interactive command can write, after a person types a sentence
naming the capital at risk. The approval is bound to the hashes of the
design, the caps and the G3 report, so changing any of them voids it.

## Key concepts

- **Event sourcing.** State = the fold of all inputs. Restart, audit and
  "what did it know then?" all come from one mechanism.
- **Decision time versus data time.** A candle that arrives late was still
  *about* its own minute, but the decision it triggers happens on arrival.
  `Engine.step(item, at)` keeps the two apart; mixing them is look-ahead.
- **Record and replay of the outside world.** The kill switch, liquidity
  and surveillance answers are written next to the step that asked, so a
  replay does not depend on today's files or database.
- **Idempotency keys and write-ahead intent.** A real order is stored
  before it is sent and keyed by (run, engine order id): a crash or a
  replay can never send it twice.
- **Never retry what may have had an effect.** A timed-out order request
  is "unknown", not "failed". Retrying it could buy twice.
- **Fail closed.** Unknown liquidity, unknown surveillance status, a book
  that does not match the broker's: each one stops trading.

## What could go wrong

- **The candle feed is unverified.** Whether Upstox's intraday reply
  includes the forming candle, and how late a finished one appears, is
  measured only when `gats probe upstox-intraday` runs with a token. The
  runtime decides by the clock precisely because this is unknown.
- **Paper fills are not real fills.** Both sides of the G3 comparison use
  the same model on one-minute bars. G3 can show that live timing did not
  break the strategy; it cannot show what the market will charge.
- **Stale revenue.** Quarterly results are loaded by a manual backfill. If
  it is not rerun, an order's size relative to revenue uses old figures.
- **Filings on non-trading days are not traded** (the engine expires or
  refuses the order), in the backtest and in paper alike.
- **The live mirror is crude.** If a real fill differs from the simulated
  one, the books drift and trading stops. That is the intended behaviour
  for a pilot, and it will be annoying.
